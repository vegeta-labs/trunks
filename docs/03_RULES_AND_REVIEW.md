## 1. 产品规则

| # | 规则 | 怎么检查 |
|---|---|---|
| P1 | **人做决定，agent 做准备。** agent 不发邮件、不动钱、不改业务记录、不做对人有重大影响的决定 | 代码里没有发送和写业务系统的路径（TC-OUT-09、TC-FRD-01） |
| P2 | **每个结论都能看到依据**：原文出处、哪条规则、哪个模型版本 | 演示时任指一个字段或风险，能说出来源 |
| P3 | **宁可误报，不能漏报高风险。** 风险只能被代码规则和人调高，模型不能调低 | 评测门槛（PRD §6）、TC-RSK-06 |
| P4 | **邮件内容是数据，不是指令。** 读邮件的模型没有任何工具 | TC-CLS-06、评测集提示注入样本 |
| P5 | **最少的数据给最少的人和系统**：外部模型只看脱敏文本；KYC 附件不给外部模型；事件和导出只有账号后 4 位 | TC-RED-*、TC-OUT-04 |
| P6 | **示例和评测数据全部虚构**；仓库里不出现任何参考平台的名字、标志或页面文字 | 发布前检查 |
| P7 | **范围纪律。** 新想法进 backlog；要做先改 PRD 并重新批准 | PR 描述必须写需求编号 |
| P8 | **只说做到了的。** 对外只讲已实现、已测试的部分，不宣称节省时间或符合监管 | 发布说明逐条对照测试 |
| P9 | **部署方自己掌控**：自托管、不接统计、不向项目作者发送任何数据 | TC-PRV-04 |

## 2. 开发规则

| # | 规则 |
|---|---|
| D1 | 判断规则只写在 `src/lib/` 纯函数里；流水线、接口、界面只调用，不自己判断 |
| D2 | 金额整数最小单位 + 币种代码；不用浮点 |
| D3 | 规则只能按 PRD §5；要改先改 PRD |

| D5 | TypeScript 严格模式；lint 零警告；构建通过 |
| D6 | 一个 PR 只做一组需求；PR 标题写需求编号 |
| D7 | 所有改动走 PR，CI 全绿才能合并 |
| D8 | 新增依赖在技术方案 §8 写理由和许可证；许可证策略见技术方案 §5（应用依赖、开发工具、外部组件三类） |

| D11 | 提示词和 JSON Schema 带版本号；改提示词必须重录回放并附评测分数对比 |

## 3. 评审流程

```
G0 需求评审 → G1 方案评审 → [冻结解除] → G2 每个 PR → G3 发布 → G4 用户反馈回流
```
**冻结：** G0 和 G1 都通过、负责人批准之前，不写实现代码。

### G0 / G1
1. Claude 写稿并自查（规则是否互相矛盾、每个验收点是否可测、例子是否手算过）。
2. 全新上下文审查代理（看不到写作过程，限时 30 分钟），用与 Codex 相同的提示词先审一轮；问题先处理。
3. Codex 交叉审核（提示词存 `docs/review/`）。
4. Claude 逐条判断：接受 / 不接受及理由，写进评审记录。
5. 有 blocker 或 major 被接受 → 改版后复审；轮数和停止条件见 `DEV_PROCESS_RULES.md`（负责人 2026-11-09 批准）。
6. 负责人批准：在 PRD 变更记录写「批准」。

### G2 每个 PR
0. **自测关卡（交 Codex 之前）：** 逐条对照 PRD §5 和代码；攻击输入（畸形 MIME、超大附件、零宽字符、同形字、提示注入、超长字段、`__proto__` 等特殊键）每类至少一个测试；变异检查（每个变异体被抓住或证明等价）；评测集全部通过；全新上下文审查代理先审一轮并修完。
1. PR 描述列出覆盖的需求编号和用例编号，不适用的完成标准写原因。
2. CI：类型检查 → lint → 单元 + 集成 → 到期用例检查 → 独立复核（Python）→ 评测 → 安全检查 → 构建 → 端到端。
3. Codex 代码审核：专找「漏报风险、泄露数据、被邮件操纵、越权写入」的路径。
4. 负责人验收本 PR 相关的清单项，留言 Accepted 并合并（或明确请 Claude 合并，Claude 在 PR 评论里写明）。

### G2a 小修通道
同 Toolkit：不改 `src/lib/`、不改风险和防欺诈规则、不改导入导出格式、源码改动 ≤ 约 5 个文件时适用；变异检查只跑改动文件；评测集照跑。

### G3 发布
1. 完整手工清单 + 全部自动测试 + 评测（含保留集）。
2. 负责人确认后打 tag、写发布说明（只列已测试的功能；推送公开仓库之前写定，见第 4 条）、更新演示站。
3. **小版本（v0.3.1）：** 保留集每套只用一次。与上次跑过保留集的版本相比，判断相关的代码和数据（`scripts/judgement-diff.mjs` 默认纳入所有文件，仅排除 `src/web/`、`docs/`（`docs/milestone.txt`、`docs/01_PRD.md`、`docs/04_TEST_PLAN.md` 除外）、`e2e/`、`e2e-demo/`、`*.test.[cm]?[jt]sx?`、`README.md`、`CHANGELOG.md`、`.github/`；包括运行、模型选择、评测控制、数据和部署输入）逐字节相同；或者不同之处逐条列出，每一处只在保留集不会出现的条件下起作用——条件由开发仓库的事实（例如评测程序固定读的文件）证明，开发仓库证明不了的由独立运行者对保留集核对（只回报是否成立，不看样本）——这时可以不跑保留集，发布说明原样引用上次的结果并写明「在 vX 上测得」和不同之处；脚本输出和核对结果附在发布记录里；开发集评测照常要跑且结果与上次相同。其他情况都要新写一套保留集。
4. **推送公开仓库（发布或只改文档，v0.3.2）：** 开发仓库是唯一来源，公开仓库只从开发仓库单向更新，不在公开仓库直接改。发布说明（`CHANGELOG.md`）和其他原样公开的文件（`README.md`、`AGENTS.md`、`docs/en/`）先在开发仓库写定、合并，再随这次推送一起带过去；正式环境冒烟后要改，也先改开发仓库再推一次。推送前：导出脚本 `scripts/public-export.ts`（含扫描）通过，先对导出目录跑 `scripts/public-manifest.ts check-publish <导出目录>`；把导出放进公开仓库的本地副本并提交后，再对这个副本跑一次 `check-publish <公开仓库副本>`（副本必须干净，检查的是已提交的内容，也就是推送出去的内容）。两次都要求：原样公开的文件与开发仓库逐字节相同，每个文件都在导出脚本的公开清单内，只在开发仓库用的文件、符号链接、含控制字符的路径都不在其中。推送后：跑 `scripts/public-manifest.ts write <公开仓库副本>`，把 `release/public-manifest.json` 开 PR 并在推送当天合并进开发仓库 main；tag 也在推送当天打好，最新 tag 等于 `CHANGELOG.md` 最新版本（`scripts/check-version-labels.ts --tag`）。开发仓库的每周检查比对公开仓库与这份清单；推送后清单或 tag 还没跟上时它会失败，提示信息会写明这个原因。
5. 发布当天看组织主页 https://github.com/vegeta-labs ：版本号由 `vegeta-labs/.github` 的每日工作流 Sync release versions 自动同步（可在它的 Actions 页手动运行，不用等第二天）；产品介绍（`profile/README.md` 的 What it does 一列）与这次发布的功能不符时，开 PR 改 `vegeta-labs/.github`，推送要负责人确认。

### G4 用户反馈
反馈只记化名和脱敏内容；分类：漏报风险或数据泄露（**立即停止推广**，先修复并补评测样本）/ 误判 / 可用性 / 新需求。

## 4. 完成标准（Definition of Done）
- [ ] 自测关卡完成并记录
- [ ] 实现符合 PRD §5 对应规则
- [ ] 每个涉及的验收点都有测试，测试名带编号
- [ ] 攻击输入和恶意样本用例存在且通过
- [ ] CI 全绿（含覆盖检查、独立复核、评测、安全检查）
- [ ] Codex 审核意见已处理并记录
- [ ] 负责人验收并留言 Accepted
- [ ] 文档同步更新；进展记录本阶段一节已更新并同步 Google Doc
