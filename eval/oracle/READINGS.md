# Oracle readings (E1)

Interpretations the oracle (`eval/oracle/oracle.py`) had to make where the PRD v0.7.7 / test plan v0.7.7 text leaves room (updated 2026-10-30 for v0.7.1, v0.7.2, v0.7.3, v0.7.4, v0.7.5 and v0.7.7; entries changed for those versions say so). Each one is also marked in the code with a `# READING:` comment. Sources read: `docs/01_PRD.md`, `docs/04_TEST_PLAN.md`, `eval/SCHEMA.md`, `eval/oracle/BRIEF.md`, and the Unicode data file `data/unicode/confusables.txt` (UTS #39 data, Unicode 16.0.0, Unicode License v3) only.

## I-04 / I-05 text
- **R-01 I-04 order (changed for v0.7.3).** NFKC, then delete every `Cf` character and every `Default_Ignorable_Code_Point`; this is repeated until the text no longer changes. The standard library has no DICP property, so the ranges are written out from DerivedCoreProperties.txt (Unicode 15) and must be checked against the Unicode version the product uses: U+00AD, 034F, 061C, 115F–1160, 17B4–17B5, 180B–180F, 200B–200F, 202A–202E, 2060–206F, 3164, FE00–FE0F, FEFF, FFA0, FFF0–FFF8, 1BCA0–1BCA3, 1D173–1D17A, E0000–E0FFF. Side effect: Hangul filler characters (U+115F, U+1160, U+3164, U+FFA0) are deleted even inside Korean text.
- **R-02 I-05 word characters (changed for v0.7.17; replaces the 2026-10-30 reading that a combining mark is a word boundary, which the PRD now contradicts).** A "letter or digit" is any Unicode character in category L* or N*; only these start a word. A combining mark M* (Devanagari vowel signs, Arabic harakat, a U+0301 that NFKC leaves standing after `t`) belongs to the letter before it and does not split the word (PRD I-05 v0.7.17). "The letter before it" is read as the word character before it: a mark after a digit, or after another mark of the same word, also stays in the word. A mark with no letter or digit before it (start of text, after a space or punctuation) belongs to no word and is a separator, so a lone mark never forms a word. Words are compared with every mark removed, both before and after Unicode casefold: `passport`+U+0301 equals `passport`, `pass`+U+0332+`port` is the one word `passport`, unvocalised `محمد` equals `محمّد`, and (a consequence of the rule) Devanagari words that differ only in vowel signs, such as `राम` and `रामू`, are the same word. A mark that NFKC composes into its base letter (`e`+U+0301 → `é`) is no longer a mark, so `passporté` is still not `passport`. C-RED-1 contact-name words: the length ≥ 3 is the number of code points of the word as written after I-04, marks included and before casefold (`राम` = र + ा + म = 3). The same tokenisation is used everywhere I-05 is used: `wordlist_match`, the C-RED-1 keyword windows (`passport`, `account`, `sort code`, `DOB` …), contact-name words in `redact` and injection markers (signal 8); the oracle has no separate pressure-word or internal-word function. C-LNK-3 name similarity keeps its own split (PRD: only ASCII non-letters separate, non-ASCII counts as a letter), and the C-RED-1 «every occurrence» and IBAN boundary checks use Python `str.isalnum` (they are not I-05 rules). C-RED-0 (KYC, added in E4) uses the same tokenisation with CJK characters turned into separators first (R-E4-02).
- **R-03 I-05 phrases.** Inside a multi-word phrase, any run of separators (spaces, punctuation, line breaks, of any length) counts as the gap between words. So `a/c` is the word sequence `a c`, and `don't tell` is `don t tell`. Case is ignored by Unicode casefold.

## I-01 / C-EXT-3 amounts
- **R-04 I-01 exact form.** `[0-9]{1,3}(,[0-9]{3})+` or `[0-9]+`, then an optional `.` with 1–2 digits. These are rejected: a leading `.` (`.5`), a trailing `.` (`5.`), a sign, and surrounding whitespace. `0` is accepted. (v0.7.1) The upper bound is inclusive: `1,000,000,000.00` is accepted, `1,000,000,000.01` is not.
- **R-05 Token boundaries.** Allowed before the token: start of text, whitespace, `(` `)` `;` `:`. A comma is never allowed before the token, because the comma would then be followed by the token, not by whitespace. Allowed after the token: end of text, whitespace, `(` `)` `;` `:`, and `,` or `.` when followed by whitespace or end of text ("句末 ." = full stop followed by whitespace or end).
- **R-06 Number part.** The number part is the maximal run of `[0-9.,]` that starts and ends with a digit. If that run fails I-01, the whole token is void; no sub-run is taken from it. "One space" means exactly one U+0020 (NBSP becomes a space under NFKC).
- **R-07 Marker case.** `US$` is matched in upper case only. `GBP`/`EUR`/`USD` are case-insensitive. Symbols may be prefix or suffix (`5 €`, `500$`).
- **R-08 Marker ownership (changed for v0.7.1).** Candidates with bad boundaries or that are void (minus sign, number part not I-01) are dropped first and occupy nothing. Of the rest, a number also belongs to one token only: two candidates conflict when their spans share a character (the marker or the number). Glued candidates (no space) are taken first, then the rest from left to right; a candidate that conflicts with one already taken is dropped. Note: under the boundary rule of R-05 a glued candidate can never conflict with another valid candidate, so the glued-first rule never changes a result; the left-first rule decides every conflict.

## MT103 / pacs.008
- **R-09 `:32A:`.** `:32A:` must not be preceded by a letter or digit. The value follows with no whitespace: `YYMMDD` + 3 upper-case letters + digits + a **mandatory** decimal comma + 0–2 decimals, with no thousands separators. An invalid calendar date, more than 2 decimals, or a currency outside GBP/EUR/USD → no item. Repeated fields are all listed (no de-duplication). (v0.7.1) The I-01 upper bound also applies to `:32A:` amounts (I-01 says only the number format differs there).
- **R-10 1 MB.** 1 MB is 1,048,576 bytes of the UTF-8 encoding (≤ is allowed).
- **R-11 DTD detection.** Any `<!DOCTYPE` or `<!ENTITY` anywhere in the XML (case-insensitive, even inside a comment) → not parsed. Malformed XML → not parsed.
- **R-12 Parsing source.** The XML is parsed from the original text, without I-04, because NFKC could create markup from full-width `＜`. I-04 is applied to the extracted values (amount, `Ccy`, dates, UETR).
- **R-12a pacs.008 text (v0.7.3).** `pacs008` also returns `text`: every element's text and tail in the whole parsed file (an `AppHdr` envelope included), in document order, each trimmed, whitespace-only pieces dropped, joined with `\n`. Attribute values (such as `Ccy`) are not included. The original characters are returned; I-04 is applied when the text is processed as attachment text. A file that is not parsed has no `text`.
- **R-13 AppHdr envelope.** The envelope is any root element whose direct children include an element with local name `AppHdr` (any namespace) and a `Document` in namespace `urn:iso:std:iso:20022:tech:xsd:pacs.008.<something>`.
- **R-14 Paths.** `CdtTrfTxInf` and `GrpHdr` are direct children of the message element(s) directly under `Document` (normally `FIToFICstmrCdtTrf`). Children are matched by local name.
- **R-15 Invalid amount (changed for v0.7.1).** Every `CdtTrfTxInf` yields an item. "The amount" is minor and currency together: a missing `IntrBkSttlmAmt`, a value failing I-01 (period decimal, upper bound) or an unsupported `Ccy` (upper-cased) makes both `minor` and `currency` null; value date and UETR are still reported.
- **R-16 Dates in pacs.008.** If `CdtTrfTxInf/IntrBkSttlmDt` exists but is not a valid ISO date, `value_date` is null. It falls back to `GrpHdr/IntrBkSttlmDt` only when the transaction element is absent.
- **R-17 UETR element (changed for v0.7.1, corrected after the Codex E1 review).** The element value (I-04, trimmed, lower-cased) is a C-EXT-1 candidate only when it is UUID-shaped (8-4-4-4-12 hex, nothing else). A v4 UUID → `uetr`; a UUID-shaped value that is not v4 → `uetr_invalid`. A value of any other shape (for example an IBAN), or an empty element, gives neither; the value is still part of the document `text`.

## C-EXT-1 / C-EXT-2
- **R-18 UETR prefix.** The prefix `UETR` written directly before the value is matched case-insensitively. `121:` and `UETR:` need no special handling, because `:` is an allowed neighbour.
- **R-19 Adjacent reference segments.** Segments are adjacent when they are consecutive, however many separator characters lie between them (including line breaks). Known references are I-04-normalised before C-EXT-2 normalisation. Output follows the order of `known`, without duplicates. An empty normalised reference never matches.

## C-EXT-4 / C-RED-1 accounts
- **R-20 IBAN shape (changed for v0.7.1).** A registered country code (either case) + 2 digits + ASCII letters/digits, total length exactly the country's length from the table in R-20a. Written solid, or in groups of 4 from the start (the last group may be shorter) with exactly one space, one line break or (v0.7.3) one hyphen between groups; a line break is `\r\n`, `\n` or `\r`; the three kinds of gap may be mixed. A tab, two spaces, two hyphens or any other grouping is not a shape. The shape must not touch another letter or digit (any script) at either end. Shapes are found left to right without overlap.
- **R-20a IBAN registry table.** Written from knowledge of the SWIFT IBAN Registry, **not** copied from a registry release; it must be checked against the release the product uses. Territories that use another country's code (Jersey, Guernsey, Isle of Man → GB; French overseas territories → FR; Åland → FI) are not listed separately. Least certain entries (recent additions): BI, DJ, FK, HN, MN, NI, OM, SO, YE.
  AD 24, AE 23, AL 28, AT 20, AZ 28, BA 20, BE 16, BG 22, BH 22, BI 27, BR 29, BY 28, CH 21, CR 22, CY 28, CZ 24, DE 22, DJ 27, DK 18, DO 28, EE 20, EG 29, ES 24, FI 18, FK 18, FO 18, FR 27, GB 22, GE 22, GI 23, GL 18, GR 27, GT 28, HN 28, HR 21, HU 28, IE 22, IL 23, IQ 23, IS 26, IT 27, JO 30, KW 30, KZ 20, LB 28, LC 32, LI 21, LT 20, LU 20, LV 21, LY 25, MC 27, MD 24, ME 22, MK 19, MN 20, MR 27, MT 31, MU 30, NI 28, NL 18, NO 15, OM 23, PK 24, PL 28, PS 29, PT 25, QA 29, RO 24, RS 22, RU 33, SA 24, SC 31, SD 18, SE 24, SI 19, SK 24, SM 27, SO 23, ST 25, SV 28, TL 23, TN 24, TR 26, UA 29, VA 22, VG 24, XK 20, YE 30.
- **R-21 IBAN validation (changed for v0.7.1).** Because the shape has an exact length, the old prefix search is gone: C-EXT-4 checks mod-97 = 1 on the whole shape (upper-cased); redaction replaces every shape whatever its check digits.
- **R-22 UK distance.** "附近 30 个字符内" means at most 30 characters lie between the sort code and the 8-digit number, on either side. Each 8-digit number pairs with the nearest sort code. The sort code is `NN-NN-NN` or `NNNNNN`. Digit runs must not touch a letter or digit, and `NN-NN-NN` must not be part of a longer hyphenated digit chain.
- **R-23 UK output.** For a UK account, `country` is null (the kind `uk` already gives the type). Duplicates are removed by account number for UK and by the full compact value for IBAN. Output follows the order of first appearance.

## C-EXT-5 dates
- **R-24 Date formats (changed for v0.7.1).** English months are accepted in full, as 3-letter abbreviations, or as `Sept`, case-insensitive, with an optional `.`. The day has 1–2 digits and may carry any of `st`/`nd`/`rd`/`th` (case-insensitive, not checked against the number, so `29st` is accepted); `of` may follow the day in day-month order, with or without a suffix (`29 of October 2026`). Parts are separated by one or more spaces or tabs, never a line break (so `20 October\n2026-10-29` is only the ISO date). An optional comma may follow the month (DMY) or day (MDY). The year must have 4 digits; a date without a year is not a date. Slash dates accept 1–2 digit parts. `.`- and `-`-separated numeric dates are not C-EXT-5 dates.
- **R-25 Slash dates.** Equal parts (`03/03/2026`) → `ok` (now PRD text, v0.7.1). Both parts > 12, a zero part, or an impossible calendar date → `invalid`.

## C-EXT-6
- **R-26 Platform domains.** A domain matches a platform when it equals the platform domain or is a subdomain of it. The first hit wins, sender domain first, then links in order.

## C-RED-1 redaction
- **R-27 Keywords.** The keywords (`sort`, `sort code`, `account`, `acc`, `a/c`, `passport`, `born`, `DOB`, `D.O.B.` (v0.7.3; under I-05 the words `d o b`, so `d-o-b` also counts), `date of birth`) use I-05 whole-word matching. `accounts` does not count.
- **R-28 Windows.** "Within N characters after word X" means the number **starts** at most N characters after the end of X. "Within N characters before or after" means at most N characters lie between them. The number may extend past the window.
- **R-29 Digit-run boundaries.** The 6/8/9-digit runs, the NI number and the driving licence must not touch another letter or digit. NI numbers and driving licences are case-insensitive. Driving licences contain no spaces. (v0.7.1) NI numbers are solid `AA999999A` or the printed form `AA 99 99 99 A` with exactly one space between the five parts; both are the same value. (v0.7.3) The driving licence's first 5 characters are 1–5 letters followed by `9`s (`LEE99…`, `L9999…`); a letter after a `9` is not allowed.
- **R-30 DOB shapes.** Dates of birth are any C-EXT-5 date shape (whatever its status), plus `DD.MM.YYYY` / `DD-MM-YYYY`. The date must start within 30 characters after `born` / `DOB` / `date of birth`.
- **R-31 Postcode line.** The postcode regex `[A-Z]{1,2}[0-9][A-Z0-9]? ?[0-9][A-Z]{2}` is case-insensitive and must not touch a letter or digit. "Its line" is the text between line breaks, without the line's leading and trailing whitespace. (Changed for v0.7.3) Up to 3 lines directly above the postcode line are added while they are non-empty (a line of only whitespace is empty and stops the walk); `\r\n` is one line break. The postcode line and those lines form **one** span (one `[ADDRESS_n]`), from the first non-space character of the top line to the last non-space character of the postcode line. Consequence: without a blank line, the 3 lines above a postcode are replaced whatever they say (a greeting, or a sort-code line, which then merges with the address under R-36).
- **R-32 Phones (changed for v0.7.1, v0.7.2, v0.7.3).** A phone starts with `+`, `00`, `0`, or `(0` (a bracketed national area code such as `(020)`); the start must not be preceded by a letter, digit or `+`. `+` and `00` are international prefixes, are not counted, and are followed directly by the country-code digits. The phone is a series of items: digit runs, or digits in brackets. Brackets are allowed only as the first item of a national number (the digits must start with `0`) or as the item right after the country code; there `(0)` is not counted, while any other bracketed area code is counted (`+1 (212) 555 0100`). Items are separated by one space or one hyphen; a bracketed item may also touch its neighbours (`(020)7946 0958`). The phone ends at the first item end where the count is 10–15 (v0.7.2); it must not be followed there by a letter or digit, otherwise there is no phone (no later cut is tried). No such point → no phone. Starts are tried at every position left to right, and a rejected start consumes nothing (fixes B1). Same value: `(0)` removed, a leading `00` read as `+`, then only digits and `+`.
- **R-33 Email shape (corrected after the Codex E1 review).** The whole RFC 5322 local part is replaced. It is either:
  - a dot-atom of atext: Python's Unicode `\w` (letters and digits in any script, plus `_`) and ``! # $ % & ' * + / = ? ^ ` { | } ~ -``, with dots only between atoms; or
  - a quoted string `"…"` with backslash escapes and no line break, replaced whole including its quotes.
  The local part must not be preceded by an atext character, `.` or `"`, so the longest valid local part is taken. A quote or apostrophe directly before an address, as in `'amelia@…`, is therefore part of the local part. The domain is word characters and hyphens with at least one dot; domain literals (`[1.2.3.4]`) are not recognised.
- **R-34 Domain kept.** The email domain is kept. A contact-name word inside an email domain is therefore **not** replaced.
- **R-35 Names.** Contact names are split into I-05 words; words with ≥ 3 code points are matched case-insensitively as whole words.
- **R-35a Every occurrence (v0.7.3).** After all rules have run, each hit's text is searched for again in the whole text (one `redact` call = one message). An occurrence is the same character sequence, case-insensitive, that does not touch a letter or digit at either end; it gets the kind of the original hit and is merged as usual. EMAIL and NAME are left out: the value of an email is the whole address, which the email rule already finds everywhere, and contact names are matched everywhere anyway; a bare local part (`info`) elsewhere is not replaced. Other spellings of the same value (`12-34-56` vs `123456`) are not searched for.
- **R-36 Union and merging.** Hits that share at least one character are merged into one span. Touching hits stay separate. The merged kind is the earliest in the C-RED-1 order: ACCOUNT, SORTCODE, ID, DOB, ADDRESS, PHONE, EMAIL, NAME. So an IBAN on an address line makes the whole line `[ACCOUNT_n]`.
- **R-37 "Same value".** Accounts, sort codes and IDs ignore whitespace, punctuation and case. Phones keep only `+` and digits. Emails and names ignore case. DOB and addresses ignore case and collapse whitespace. `n` is numbered per kind, in order of first appearance.

## C-LNK-3
- **R-38 Normalise first.** I-04 is applied to both names first, as TC-SIG-08 requires for display names.
- **R-39 No words.** When either side has no words, the result is reported as `{num: 0, den: 0}` (similarity 0).

## C-SIG-1 / C-SIG-3
- **R-40 authserv-id.** It is the first token of the header value, compared case-insensitively. A header without one counts as untrusted. `untrusted_auth_header` is computed for every adapter, including `.eml`.
- **R-41 Several results (changed for v0.7.3).** With several results for one method, any failing one fails. `dmarc_pass` needs at least one dmarc result and **every** dmarc result `pass` (results that disagree, e.g. `pass` and `none`, are not a pass). `auth = "pass"` still means an adopted header exists and nothing failed, even if dmarc is `none`, absent or disagreeing.
- **R-41a Header syntax (RFC 8601).** Comments `( … )` may nest; inside a comment, quotes are ordinary text and `\` escapes the next character. Outside comments, a quoted string `"…"` (with `\` escapes) is one value, and any `;`, `=` or `(` inside it is not result syntax. Comments are dropped and quoted strings blanked before splitting on `;`. Each resinfo is `method[/version] = result`; the rest of the segment is ignored.
- **R-42 Adoption.** Results are adopted only for adapters `gmail`/`graph`/`imap` with `mailbox_strips_auth_results = true`; never for `eml`.
- **R-43 display_name_mismatch (resolved by v0.7.1).** True when at least one contact's name has similarity 1 with the display name and the sender address is not an address of any of those contacts (PRD text now says so).
- **R-44 lookalike_domain steps.** The steps are:
  - Domains are lower-cased and `xn--` labels decoded.
  - "Not in the name list" is exact membership.
  - Equality after stripping `www.` is not a lookalike.
  - Distance is **unrestricted** Damerau-Levenshtein, not optimal string alignment.
  - The PRD's own look-alike table is applied to both sides, multi-letter entries first (`rn→m`, `vv→w`, then `0→o`, `1→l`, `i→l`).
  - "Non-Latin" means a letter whose Unicode name does not start with `LATIN`.
- **R-45 Skeleton (corrected after the Codex E1 review).** This is full UTS #39: skeleton(X) = NFD(each character of NFD(X) replaced by its prototype from `data/unicode/confusables.txt`). It is applied to both domains after lower-casing and `xn--` decoding, and only when the sender domain has a non-Latin letter.
  - The skeleton is case-sensitive, as UTS #39 defines it. A non-Latin letter whose look-alike is a Latin capital (`0→O`, Cherokee `Ꭺ→A`) therefore does not match a lower-case Latin domain by skeleton alone (Cherokee Ꭺ lower-cases to ꭺ, whose skeleton is `ᴀ`).
  - The data also maps Latin letters (`m→rn`). That is harmless, because both sides are mapped.
- **R-46 Reply-To.** Reply-To may be a bare address or `Name <addr>`. It is compared in full after I-03 lower-casing. An empty value counts as absent.
- **R-47 first_time_sender.** True when the sender address (I-03) is in neither `prior_from_addresses` nor any contact's emails.
- **R-48 hidden_text (changed for v0.7.3, v0.7.4 and v0.7.5).** The rules are:
  - Default colours are black text on a white background.
  - Browser default colours (v0.7.5, from the TC-SIG-09 v0.7.5 examples):
    - `<body text="…">` sets the text colour, like `<font color>`; both are presentational attributes and rank below every author style.
    - An `<a>` with an `href` (any value) is a link and gets the browser's link colour `#0000ee` (unvisited) from the default sheet; it does not inherit the parent's colour, and a `<font color>` around it does not change it. An author style on the `<a>` (inline, or a sheet rule such as `a{color:#000}`) overrides it. An `<a>` without `href` is not a link and inherits as usual.
    - `<body link="…">` replaces the link colour (HTML Standard rendering section); `vlink`/`alink` are ignored (links are taken as unvisited).
    - CSS-wide keywords (changed for v0.7.7, now PRD text): for `color`, `inherit`, `unset`, `currentcolor` take the parent's colour, `initial` is black (so `a{color:inherit}` makes a link inherit). `revert` and `revert-layer` give the browser default colour: for a link (an `<a>` with `href`) the link colour (`#0000ee`, or the colour `<body link>` set; that last part is a reading), for any other element the parent's colour. For `background-color`, `currentcolor` is the element's text colour (so it hides the text), and `inherit`, `unset`, `initial`, `revert`, `revert-layer` leave the background behind the text unchanged.
  - `display:none`, `visibility:hidden`, `opacity:0` (any zero value: `0`, `0.0`, `0%`) and tiny font sizes hide all descendants. Opacities do not multiply (`0.1` inside `0.1` is visible).
  - Font size hides text at 0 in any unit, or at ≤ 1 in px or with no unit. (Corrected after the Codex E1 review) The `font` shorthand sets the size too. Its tokens before the size are style, variant, weight or stretch keywords or a unitless weight; the first other token, cut at `/`, is the size, and a unitless `0` counts as a size (`font:0/0 a` is hidden). A system font keyword alone (`font: caption`, `icon`, `menu`, `message-box`, `small-caption`, `status-bar`) sets the system's size, which hides nothing, so it still overrides an earlier size. (Changed after Codex round 5) The size token must be a valid font size: a size keyword (`xx-small` … `xxx-large`, `larger`, `smaller`), a number with a CSS length unit or `%`, or a zero. Otherwise the shorthand has no valid size, is invalid CSS and is dropped at parse time like a negative one, so an earlier or lower-priority size stays in effect (`font-size:1px; font:bold Arial` and `font:12foo Arial` after `1px` are hidden). A size written with a function (`calc()`, `var()`) is outside the evaluated scope (PRD v0.7.6) and keeps the old treatment: a size that hides nothing. (v0.7.7, now PRD text) A size whose numeric value is 0 is 0 however it is written, in `font` and `font-size` alike: a CSS number with an optional sign, fraction and exponent (`0`, `00`, `0.0`, `.0`, `-0`, `+0`, `0e3`, with or without a unit); a unitless one in `font` is a size, not a weight. A negative non-zero size is invalid CSS and hides nothing (now PRD text, v0.7.7). (Changed after Codex round 5) As in CSS, the invalid declaration is dropped when it is parsed: it takes no part in the cascade, so an earlier or lower-priority valid size (inline, style sheet, `!important` or inherited) stays in effect (`font-size:1px; font-size:-1px` is hidden). A `font` shorthand with a negative size is invalid as a whole and dropped (`font-size:1px; font:-1px Arial` is hidden); a negative unitless number in `font` counts too, since it is no valid weight. `-0` is still zero, not negative. (v0.7.4, now PRD text) `font` and `font-size` take part in the cascade as one property: the later one written wins, other things being equal.
  - Colour comes from `style` or `<font color>`; background from `background`, `background-color` or `bgcolor`; both are inherited. (v0.7.4) `background` is expanded into `background-color` and cascades with it, so the later one written wins: its colour token, or the initial value `transparent` when it has none (`background:url(x)` after `background-color:#000` resets the colour; a transparent background then keeps the inherited one). A transparent background keeps the inherited one. Text whose colour is `transparent`, or has alpha 0 (`rgba(…,0)`, `#rrggbb00`), is hidden.
  - Style sheets: rules from every `<style>` element apply to the whole document, wherever the `<style>` sits. Supported selectors are type, `*`, `.class` and `#id` and compounds of these, the descendant and `>` combinators, and comma lists. A selector with anything else (attributes, pseudo-classes, `+`, `~`) is ignored.
  - At-rule blocks (changed for v0.7.4; the old "all at-rule blocks are ignored" reading is gone). Rules inside `@media` count when at least one query of its comma list, lower-cased with whitespace collapsed, is exactly `all`, `screen` or `only screen` (`@media only screen, print` counts; `@media screen and (max-width:600px)` does not). An empty query list (`@media {…}`) is `all` in CSS and counts. Every `@supports` block counts whatever its condition, and every `@layer` block counts (its cascade order is in the layer point below). Blocks nest: a counted block inside a counted block counts, anything inside a block that does not count is ignored. Every other at-rule block (`@font-face`, `@keyframes`, `@page`, …) is ignored. Statement at-rules (`@import url(x.css);`, `@layer a, b;`) are not part of the following rule's selector; `@layer` statements declare layer order (below).
  - Cascade (changed for v0.7.4; `!important` is no longer ignored). For each property the winner is the declaration with the highest key (`!important`, inline, specificity (ids, classes, types), rule order, position in the block): `!important` beats everything without it (an inline `!important` beats a sheet `!important`), then inline style beats the sheet, then specificity, then the later rule. `!important` may be written with spaces (`! important`). The browser default style sheet and the presentational attributes `<font color>`, `<body text>` and `bgcolor` rank below every author rule, layered or not, the defaults lowest of all (UA `!important` is not modelled).
  - `@layer` cascade (v0.7.5; replaces the old reading "`@layer` order is not modelled; layered rules cascade like unlayered ones"). The PRD text is implemented as CSS Cascade 5 orders it. The cascade key is (`!important`, inline, layer, specificity, rule order, position in block):
    - Layers form a tree. A layer's normal-declaration rank is its position in a post-order walk: sub-layers in order of first appearance, then the layer's own rules; the root (unlayered rules) comes last, so it beats every layer, and a parent's own rules beat its sub-layers. `!important` declarations use the negated rank, which reverses the whole order (earlier layers win, layered beats unlayered, a sub-layer beats its parent's own rules).
    - Inline style stays above all sheet rules for normal declarations, and inline `!important` above all sheet `!important` (layered included).
    - A layer is declared where its name first appears: an `@layer` block, an `@layer a, b;` statement (in any counted block, at the top level or inside a layer), or `@import … layer(a)`. `@layer a.b` declares `a` and then `a.b`; `@layer a.b{…}` and `@layer a{@layer b{…}}` are the same layer. Names are relative to the enclosing layer.
    - Each nameless `@layer {…}` is a new layer of its own, at the point where it appears.
    - Layer names are case-sensitive identifiers (dotted lists of them). A block prelude that is not one name (e.g. `@layer a, b {…}`) is invalid and the whole block is ignored.
    - Layers declared only inside a block that does not count (e.g. `@media print`) are not declared: everything inside such a block is ignored. An `@layer` inside a counted `@media`/`@supports` block keeps the enclosing layer context.
  - Only non-whitespace text counts. Text inside `script`, `style` and `title` is ignored (code, or the window title). (Changed for v0.7.3 clarification) `head`, `template` and `noscript` are no longer simply ignored; see the next point.
  - Browser default style sheet (v0.7.3 clarification). The parts of the HTML Standard's default style sheet that hide content are applied with the lowest priority:
    - `display:none` for an element with a `hidden` attribute (any value, `until-found` included), for `head`, `template`, `datalist`, `noembed`, `noframes` and `rp`, and for a `dialog` without `open`.
    - Inside a `details` without `open`, everything except its first `summary` child is not shown, including bare text.
    - An author style (sheet or inline `display:block`) overrides these defaults as in a browser, except the closed-`details` rule.
    - `noscript` is shown, because mail clients run no scripts.
- **R-49 Comments (changed for v0.7.1).** HTML comments never set `hidden_text`, whatever their length or content (conditional comments included; fixes B2). Downlevel-revealed `<![if …]>` / `<![endif]>` declarations carry no text.
- **R-50 Injection scan.** Besides `texts`, the HTML body's text (all text nodes and comments, hidden or not) is scanned for injection phrases. Each text is scanned separately; a phrase cannot span two texts. (v0.7.1) A comment is scanned twice: as its raw content (tags act as separators, so `<!--[if mso]><p>ignore previous</p>…-->` matches) and with the tags inside it removed (so `<!-- do not<b> flag -->` matches as well).
- **R-51 Authenticated sender.** `authenticated_sender` accepts either the signals input itself or `{"signals_input": …}`. `contact_id` is returned only when the sender is authenticated. Authentication needs exactly one contact matching the address (C-LNK-1), an adopted result with `dmarc=pass`, and no spf/dkim/dmarc failure.

## C-AUD-1
- **R-52 JCS.** JCS is implemented for null, booleans, strings, integers, arrays and objects:
  - Keys are sorted by UTF-16 code units.
  - Strings are escaped as ECMAScript `JSON.stringify` does (`\b \t \n \f \r`, other C0 controls as lower-case `\u00xx`, everything else literal).
  - Integers beyond ±(2^53−1), non-integer numbers and lone surrogates are rejected.
- **R-53 Chain check.** `hash` is excluded from the hashed object. `verify_chain` checks, in this order: seq = position (from 1), `prev_hash` link (first = 64 zeros), recomputed hash. It reports the first failing record by its own `seq`.

## Currencies
- **R-54 Supported set.** The supported set is fixed to the PRD default: GBP, EUR, USD.

# Oracle readings (E3)

Written 2026-10-30 from PRD v0.7.12, test plan v0.7.11, `eval/SCHEMA.md` and `eval/oracle/BRIEF.md` part 2 only. Each is marked `# READING:` in `oracle.py` or `check_actual.py`.

## Calendar and time limits (C-RTE-1, C-RTE-2, R-RTE-02)
- **R-E3-01 Bank holidays used in the self-check.** England and Wales 2026: 2026-01-01, 04-03 (Good Friday), 04-06 (Easter Monday), 05-04, 05-25, 08-31, 12-25, 12-28 (Boxing Day substitute). One check adds 2027-01-01. The oracle itself only uses the `holidays` list it is given.
- **R-E3-02 Local dates.** Any day comparison or count (C-RSK-2a receive day, C-DRF-4 receive day and "payment date later than receive day") uses the date of `received_at` in the deployment time zone. A plain `YYYY-MM-DD` is taken as it is.
- **R-E3-03 Day count.** `working_days_after(from, to)` = working days d with from < d ≤ to; 0 when to ≤ from (callers check the order first).
- **R-E3-04 Working hours.** Counted in local wall-clock time inside each working day's period, so 09:00–18:00 is 9 hours on a clock-change day too. A start outside the period moves to the next period start. A limit ending exactly at the end of a period is that end time (18:00), not 09:00 the next working day. Output is ISO UTC with seconds (milliseconds only when non-zero).
- **R-E3-05 Follow-up (C-RTE-2).** 10 working days = `due_at` with 10 × day length working hours (the brief's definition), i.e. the same local time 10 working days later. `follow_up_at` returns null when disabled, when the Case is closed, or when no adopted class is one of the three payment classes.
- **R-E3-06 due_state.** Shares are measured in working time: `due_soon` when the remaining working time from `now` to `due_at` is ≤ `remind_share` × working time from `received_at` to `due_at`; `overdue` only when `now` is strictly later than `due_at`.
- **R-E3-07 Queue (R-RTE-01).** The queue is that of the adopted class with the highest risk floor, ties by §3.1 order (adopted labels only, C-CLS-6).

## Risk (C-RSK-1 to C-RSK-3)
- **R-E3-08 Unknown signals.** A signal that is null (unknown) does not count as hit for C-RSK-2 / C-RSK-2a.
- **R-E3-09 Amount sets.** A and B are compared as (minor units, currency) pairs; the same number in another currency is not in the intersection.
- **R-E3-10 Order of steps.** Any C-RSK-2 hit → high. Otherwise computed = C-RSK-1 floor + one step per C-RSK-2a clause hit, capped at high. The pressure clause and the closing clause each count once. Pressure text is matched with I-05 (so `don't tell` is the words `don t tell`).
- **R-E3-11 Reasons for R0.** `reasons` = the label classes (adopted + low) whose floor is above the adjustment level L (with no adjustment: every label class), in class-table order, then the clause IDs hit, in the brief's order. A clause ID is a reason only when its full condition holds (pressure words without a pressure class are not a reason).
- **R-E3-12 Adjustment input.** An adjustment that is already void is passed as null by the caller ("permanently void" is state the caller keeps). L = C0 at set time means no adjustment (③); the oracle returns the computed risk for it. A lowering is void when computed > C0 or any current reason is not in R0; a raise is never void.
- **R-E3-13 Permission (C-RSK-3 ②).** `risk_adjust` compares L with the current final risk: lower → approver role and a reason with a non-whitespace character; otherwise anyone. `cancels` = L equals the current computed risk (③).
- **R-E3-14 Empty adopted set.** With no adopted label, `unclassified` is adopted (C-CLS-2), in `risk`, `template` and `actions`.

## Disclosure, ledger, templates (C-LNK-5, C-DRF-2 to C-DRF-6)
- **R-E3-15 Ledger investor_id.** A ledger row counts for the commitment when its `investor_id` equals the bare investor ID or the commitment key. Currencies are compared in upper case. An empty or missing currency in a row counts as the deal currency — the PRD now fixes this (v0.7.14: C-DIR-3 «空单元格按交易币种», C-DRF-6 notes the import fills it); a non-empty other currency still does not count. An empty ledger list (a ledger imported, no rows) → `not_received`; `ledger: null` → `unknown`.
- **R-E3-16 Primary class.** `unclassified` is a primary-class candidate only when it is the only adopted label; it has no default template. `primary` is returned whatever step chose the template (null when only `unclassified` is adopted).
- **R-E3-17 Payment-date source (C-DRF-4).** Evidence value dates present: one distinct date → it; several distinct → unknown. Without evidence: both `value_date` and `payment_date` present and different → unknown; else the primary class's field (`payment_evidence` → `value_date`, `payment_query` → `payment_date`), falling back to the other field when the primary's is empty. A field marked `multiple` makes the date unknown (PRD §6 rule input); a `void` field counts as empty (single-value projection). A value that is not a calendar date is invalid → `payment_need_evidence`.
- **R-E3-18 reply_check.** The C-FRD-3 list plus the extra terms, I-05 whole-word matching after I-04; hits are listed in list order (`cooling off` hits both `cooling-off` and `cooling off`).
- **R-E3-19 Sentences (C-DRF-2 ③).** A sentence ends after `.`, `!` or `?` followed by whitespace or the end of the line; a line break always ends a sentence. A sentence is removed with the whitespace after it; a line whose sentences are all removed is removed with its line break. "No value" = null, a missing key, or an empty / whitespace-only string. Values are inserted literally once (a value is never read as a placeholder); sentence splitting is done on the template text before values are inserted.
- **R-E3-20 Recipients (C-DRF-2 ④, C-SIG-1.5 v0.7.15).** Addresses are compared after I-03 lower-casing; `Name <addr>` is accepted (the address inside `<>` counts, never the display name). For a Case reply, From is always allowed and Reply-To only when it is a single non-empty value and `reply_to_mismatch` is exactly false; `reply_to` given as a list of several header values, or `reply_to_mismatch` null (unknown), → From only. For `notify_old_contact`, only the directory email.

## Actions (C-OUT-3)
- **R-E3-21 Placeholders in details.** A `details` placeholder whose value is null is rendered as an empty string (no sentence removal there). Fields use the single-value projection, so `multiple` / `void` count as empty (`request_withdrawal_consent`, `review_terms_change`).
- **R-E3-22 One action per row.** `legal_documents` and `tax_certificates` together give one `forward_to_legal`; `payment_query` and `payment_evidence` together give one action per row.
- **R-E3-23 record_lead_confirmation.** Uses the appendix A condition as given in the brief's inputs (`closing_confirmation` adopted, `confirms` = yes, confirmed by a person, authenticated sender, sender is the deal's lead); "first time" (emit once) is event state and not modelled.

## Consistency check (`check_actual.py`)
- **R-E3-24 Template from the oracle's risk.** The template is recomputed with the oracle's own risk, not the system's, so a risk mismatch usually shows a template mismatch too. No manual adjustment is applied.
- **R-E3-25 C-SIG-3 and C-LNK-5 from raw inputs (test plan v0.7.12).** `sender_contacts` deduplicated by `contact_id`; authenticated = exactly one contact, `dmarc_pass` is true, and the signal `auth_fail` is not true («任何一项失败»). May disclose = authenticated and `links.investor_id` (the commitment key) is in that contact's `investor_ids` or `authorised_for`; a bare investor ID in those lists does not match (C-DIR-2 lists keys). The old boolean fields and the `--contacts` option are gone; old booleans in a record are ignored.
- **R-E3-26 Amount set B and pressure texts.** Set B is `amounts_body`, set A `rule_output.amounts_attachment` (`rule_output.amounts` is no longer used). Pressure words: I-05 over each of `pressure_texts` on its own (a phrase does not run across two texts); the C-RSK-1 label-set condition (adopted + low) is applied in `risk`. The test plan includes the HTML body text in `pressure_texts`; the oracle uses whatever texts are exported.
- **R-E3-27 Account shape (C-RSK-2).** «IBAN 形状的串或英国账号» = any C-RED-1 `[ACCOUNT]` hit in any of `account_texts`, regardless of check digits: IBAN shapes, 8-digit numbers within 30 characters after account / acc / a/c or around «sort code», and the C-EXT-4 UK pairs. A sort code alone, or a bare 8-digit number with no keyword or sort code, is not an account. Each text is normalised (I-04) and scanned on its own.
- **R-E3-28 Ledger state from raw inputs (C-DRF-6).** No linked commitment, `commitment: null` or `commitment.ledger: null` → unknown (with no link the template is `payment_need_reference` anyway). Otherwise `ledger_state` with the bare ID = the part of the key after `::`, the key itself, `deal_currency` and `cash_due_minor` (R-E3-15: either ID form counts, an empty currency is the deal currency).
- **R-E3-29 Several Reply-To headers (C-SIG-1.5 v0.7.15).** In `signals`, `reply_to` may be a list of header values: one value → that value; several → `reply_to_mismatch` null (unknown, not counted by C-RSK-2a, R-E3-08). The «发件人无法确定» flag is Case state and not modelled.

With the C-DRF-5 templates (`payment_received` only) this changes no result: C-DRF-4 picks it only when received, and it is already `discloses_record`.

# Oracle readings (E4)

Written 2026-11-01 from PRD v0.7.18, test plan v0.7.13, `eval/SCHEMA.md` and `eval/oracle/BRIEF.md` part 3 only. Each is marked `# READING:` in `oracle.py` or `check_actual.py`. Function: `kyc` (C-RED-0 for one top-level attachment of the test plan §3 `attachments` export).

## C-RED-0 possibly-KYC attachments
- **R-E4-01 Attachment tree and the text pool for ②.** A top-level attachment is «possibly KYC» when any clause ①–⑤ holds for it or for any attachment nested in it, at any depth (R-RED-02 «递归检查嵌套附件»; TC-RED-04 «嵌套 .eml 里的护照 PDF → 外层附件是»). So a nested file name hit (①), a nested image (③), a nested PDF page without text (④) or a nested parse failure (⑤) makes the outer attachment possibly KYC; `clauses` is the union over the whole tree, in order. For ② «全部文字内容（含嵌套附件）» the `text` of the attachment and of every descendant form one pool: the MRZ is looked for line by line in each text; the ① words and `date of birth` / `place of birth` / `nationality` are matched in each text on its own (a phrase never runs across two texts); «任意两个» counts distinct words over the whole pool. So `date of birth` in an outer `.eml` and `place of birth` (or `nationality`) in the PDF inside it hold ② for the outer attachment; the same word twice counts once. File names are not part of the text pool (only ①).
- **R-E4-02 CJK characters and Chinese words.** The ① list is matched in the file name and (for ②) in each text after I-04, with I-05 whole words (incl. the v0.7.17 combining-mark rule; case by casefold, which covers «转小写»), after every CJK character has been replaced by a separator: CJK radicals, unified and compatibility ideographs incl. extensions (U+2E80–2FDF, 3005–3007, 3021–3029, 3031–3035, 3038–303C, 3400–4DBF, 4E00–9FFF, F900–FAFF, 20000–323AF), Hiragana and Katakana (U+3040–30FF, 31F0–31FF, half-width FF66–FFDC incl. half-width Hangul), Hangul Jamo, compatibility Jamo, extended Jamo and syllables (U+1100–11FF, 3130–318F, A960–A97F, AC00–D7FF). The six Chinese words are plain substrings of the I-04 text (`附件身份证明.pdf` contains `身份证` → hit). Consequences of the whole-word rule: `passports2026.pdf`, `licensed_…`, `poached_…`, `dnipro_…` do not hit; `_`, `-`, `.`, spaces and apostrophes (`'` or `’`) separate words, so `Kontoauszug_2026.pdf` and `Carte d’identité.pdf` hit.
- **R-E4-03 Machine-readable zone (changed for PRD v0.7.19).** Rule text: a line starting with `P`, characters 2–5 all upper-case letters or `<`, and `<<` somewhere in the line; leading whitespace allowed. Readings: a line is split at every line break `str.splitlines()` knows (LF, CR, CRLF, VT, FF, FS/GS/RS, NEL U+0085, U+2028, U+2029); «空白» before the `P` is any run of whitespace characters (`str.isspace`: spaces, tabs, U+3000 …), and characters 2–5 are counted from that `P`; «大写字母» = ASCII `A`–`Z` after I-04 (full-width `Ｐ＜ＧＢＲ…＜＜` folds and counts); the `<<` may be anywhere in the line, including inside characters 2–5 (`P<D<<MUSTERMANN…`); a line shorter than 5 characters after the whitespace is not an MRZ. So `P<D<<…`, `PMGBR…<<…` → yes; `PAYMENT DETAILS FOR APRIL` (no `<<`), `P<GBR` with `<<` only on the next line, lower case (`Pay<<now`), a digit in characters 2–5, `P<` in the middle of a line → no. Consequence of the text: an ordinary line such as `PAY<<NOW` has the shape and counts (an over-hold, which C-RED-0 accepts). Replaces the 2026-11-01 reading for the v0.7.18 rule «`P<` + 3 upper-case letters».
- **R-E4-04 Attachment type from `kind`.** The test plan does not list `kind` values. A MIME type (`image/png`, `application/pdf`, `message/rfc822`, `application/xml` …) or a short token (`image`, `png`, `jpeg`, `pdf`, `eml`, `xml` …) are both accepted, case-insensitive; any `image/*` MIME type or an image token (png, jpeg, jpg, gif, bmp, tiff, tif, webp, heic, heif, svg, ico) is an image (③). Only when `kind` is missing or generic (`other`, `unknown`, `binary`, `application/octet-stream`) does the file-name extension decide.
- **R-E4-05 PDF without text layer (④).** For a PDF with `parse_status: ok`, ④ holds when `pdf_pages_without_text` ≥ 1, when either page count is missing or `pdf_pages` is 0, or when the extracted text is empty or whitespace only (no extractable text). A PDF that was not parsed is covered by ⑤.
- **R-E4-06 Could not check (⑤).** Every `parse_status` other than `ok` holds ⑤: `failed`, `timeout`, `over_limit`, `encrypted`, `too_deep`, `unsupported` (unknown type, incl. XML that is not a recognised pacs.008 or that has a DTD, C-ING-2) and also `blocked` (the virus scan stopped it, so the check was never done); an unknown status value also counts. Exception: an image that is `unsupported` only because images are never parsed (no OCR) is covered by ③ and does not add ⑤. Depth: the top-level attachment is level 1, its children level 2, and so on; any node at level 4 or deeper holds ⑤ whatever its exported status («嵌套超过 3 层», C-ING-2 «EML（递归，深度 ≤ 3）»), so `eml → eml → eml → anything` is possibly KYC.
- **R-E4-07 Consistency check.** `check_actual.py` compares only top-level attachments (a child's own `maybe_kyc`, if exported, is ignored), reporting `<id> attachment <ordinal> maybe_kyc system=… oracle=…`; a missing or non-boolean system value is a mismatch. Without the option `--require-attachments`, a file without `attachments` (or with `null`) gets no KYC check; with it (accepted before or after `<dir>`), such a file prints `<id> attachments missing` and counts as a mismatch. An empty list is a valid export (no attachments) in both modes. The KYC comparison runs even when the E3 risk / template recompute of that file fails (that failure is reported on its own line).
